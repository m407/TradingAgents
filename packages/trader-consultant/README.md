# Trader Consultant

Независимый Python-пакет для подготовки **проекта приказа на перебалансировку**.
Принимает готовый снимок портфеля и рекомендации основного TradingAgents.
Модель предлагает распределение, обычный код проверяет ограничения и рассчитывает
количества. Пакет не получает брокерские ключи, не подтверждает и не исполняет сделки.

## Установка и вызов

Из корня репозитория:

```bash
pip install ./packages/trader-consultant
```

Пакет не зависит от приложения TradingAgents или терминала Trading-R1. Передайте
уже настроенную LangChain chat model с поддержкой
`with_structured_output(AllocationProposal)`. Она остаётся ответственна за
провайдера, авторизацию, тайм-ауты и транспортные повторы. Дополнительный вызов
LLM для объяснения не нужен. LangChain устанавливает вызывающее приложение;
базовый пакет использует совместимый интерфейс без импорта провайдеров.

```python
from datetime import datetime, timezone

from trader_consultant import ConsultationRequest, TraderConsultant

def propose_rebalance(model):
    now = datetime.now(timezone.utc)
    request = ConsultationRequest.model_validate({
        "snapshot": {
            "snapshot_id": "broker-snapshot-001",
            "as_of": now,
            "currency": "USD",
            "free_cash": "1000",
            "complete": True,
            "has_active_orders": False,
            "positions": [{
                "ticker": "AAPL.US",
                "kind": "stock",
                "currency": "USD",
                "quantity": "2",
                "available_quantity": "2",
                "price": "200",
                "price_at": now,
                "quantity_step": "1",
            }],
            "excluded_assets": [],
        },
        "recommendations": [{
            "ticker": "AAPL.US",
            "action": "BUY",
            "rationale": "Обоснование из основного TradingAgents",
        }],
        "policy": {
            "buy_budget": "400",
            "cash_reserve": "300",
            "max_weights": {"AAPL.US": "0.6"},
            "commission_rate": "0.001",
            "slippage_rate": "0.005",
            "minimum_trade": "50",
            "max_snapshot_age_seconds": 300,
            "max_price_age_seconds": 120,
            "order_ttl_seconds": 120,
            "max_attempts": 10,
        },
    })
    return TraderConsultant(model).consult(request)

```

Денежные значения и доли передавайте как Decimal или десятичные строки.
Пример синтетический: цены, лимиты и издержки здесь не являются рекомендацией.

## Контракт входа

- **Snapshot:** идентификатор, время с часовым поясом, выбранная валюта, свободные
  деньги, полнота данных и явный признак наличия активных заявок.
- **Position:** точный идентификатор инструмента, stock/etf, валюта, количество,
  доступное к продаже количество, положительная цена и её время, шаг количества.
  Новый BUY-кандидат также присутствует здесь, с нулевыми количествами.
  Все управляемые инструменты имеют одну валюту; отрицательные количества запрещены.
  Количества должны быть кратны шагу. Символы не нормализуются и не угадываются.
- **ExcludedAsset:** идентификатор и причина исключения. Облигации, другие валюты,
  REPO и прочие неподдерживаемые инструменты нужно перечислить здесь, а не считать
  нулевыми позициями. Их стоимость не входит в управляемый NAV.
- **Recommendation:** один из BUY, SELL, KEEP; один тикер не может встречаться дважды.
  Необязательное rationale передаётся LLM как недоверенное свидетельство.
- **Policy:** обязательные внешние максимальные веса всех управляемых позиций и
  кандидатов, бюджет покупок, резерв, оценки комиссий/проскальзывания, минимум
  сделки, ограничения возраста данных и срок действия проекта.

Вызывающее приложение отвечает за полноту снимка, биржевые календари,
доступность инструментов, разрешения и сопоставление тикеров разных источников.
В существующем `PortfolioContext` TradingAgents недостаточно данных для этого
контракта: нужны цены, их времена, шаги, доступные количества и внешние лимиты.
Для Freedom следует использовать подробный результат брокерского адаптера
и дополнить его отсутствующими полями; готового live-адаптера здесь нет.

Если источник отдаёт `Buy/Hold/Sell`, вызывающий код явно сопоставляет их с
`BUY/KEEP/SELL`. `Overweight/Underweight/REVIEW` не имеют скрытого преобразования:
решение об их значении остаётся у вызывающего приложения.

## Распределение и приказ

1. Проверить вход до вызова LLM. Неполные/устаревшие данные, активные заявки,
   отсутствующие лимиты или заведомо невыполнимая обязательная сделка блокируют
   **весь** результат.
2. LLM возвращает `AllocationProposal`: общую сумму покупок до расходов,
   конечную долю для каждого SELL, общее объяснение и причины по рекомендациям.
3. Код распределяет сумму поровну в денежном выражении между BUY-кандидатами.
   При достижении максимальной доли одного кандидата остаток перераспределяется
   между другими. Если достигнуты все потолки, остаток сохраняется деньгами.
   Это равенство **новых вложений**, а не итоговых размеров позиций.
4. Рассчитать целевые доли, округлить количества вниз к допустимому шагу.
   После округления денежные суммы могут отличаться. Остаток не расходуется
   скрыто на дополнительные лоты; в проекте есть `unused_purchase_amount`.
5. Проверить направление, минимальную сумму, доступные количества, максимальные
   веса и финансирование. BUY/SELL требуют ненулевой сделки; KEEP и позиции без
   рекомендаций сохраняются. Нарушение одной сделки блокирует весь приказ.
6. При ошибке ответа LLM передать конкретные ошибки для исправления. Максимум
   10 вариантов плана **всего**, включая первый; можно настроить меньше.
   Успех завершает цикл сразу. Ошибки доступа/транспорта модели не запускают
   повторные планы. Свежесть данных проверяется до и после обращения к модели.

**База долей фиксирована:** исходный управляемый NAV = свободные деньги +
сумма количества × цены снимка. `current_weight`, `target_weight`,
`achieved_weight` и максимумы используют один и тот же исходный NAV.
Это доли относительно снимка, не обещание будущих долей после расходов и движения
цен. `weight_basis_nav` записан в приказе. Исходное превышение максимума
предупреждается; количество можно сохранить или сократить, но не увеличивать.

Для BUY расчётная цена = цена снимка × (1 + slippage_rate), для SELL —
× (1 − slippage_rate). Комиссия = расчётный оборот сделки × commission_rate.
`buy_budget` ограничивает покупки **включая** эти расходы.
Текущие свободные деньги должны покрывать покупки и их комиссии, сохраняя
резерв. Каждая продажа оплачивает свою комиссию из собственной выручки;
выручка от SELL не используется для финансирования покупок этого приказа. `estimated_cash_after` уже включает ожидаемую выручку от продаж.

`minimum_trade` проверяется по стоимости сделки в ценах снимка. Модель комиссии
пропорциональная, без минимальной фиксированной комиссии и налогов. Вызывающий
код должен задавать консервативную оценку и отдельно сверять фактический тариф.
Расчётный запас цены — оценка расходов, **не брокерская лимитная цена**.

## Результат и подтверждение

`ConsultationResult.status`:

| Статус | Значение |
| --- | --- |
| awaiting_confirmation | Есть проект приказа; пользователь его ещё не подтвердил |
| blocked | Есть причины отказа; приказ отсутствует, частичных сделок нет |
| no_changes | Только KEEP или пустой список рекомендаций; приказ не требуется |

Даже KEEP-only запрос проходит проверку снимка. Ошибки схемы при передаче dict
возвращаются как blocked; при самостоятельном конструировании Pydantic-моделей
ошибки схемы возникают в конструкторе.

Проект содержит идентификатор, SHA-256 отпечаток полного входа, ссылку на снимок,
срок действия, сделки, объяснения, текущие/целевые/достижимые доли, денежный
резерв и список выполненных проверок. Срок ограничен TTL и оставшимся сроком
свежести снимка/цен. Исключённые активы сохраняются в результате.

У пакета нет методов confirm/place_order. Перед подтверждением внешнее
приложение должно проверить срок и актуальность счёта; изменение цен, денег,
позиций, заявок или политики требует нового расчёта. UUID и отпечаток — связь
с входом, не криптографическая подпись и не гарантия идемпотентности брокера.
Десять попыток не гарантируют успешного подбора: некоторые обязательные
рекомендации несовместимы с ограничениями.

## Проверки

```bash
cd packages/trader-consultant
uv sync --locked --group dev
uv run --locked pytest -q
uv run --locked ruff check src tests scripts
```

Из корня `mise run consultant:check` проверяет lockfile, стиль, тесты и установку
wheel в чистое окружение. Общий `mise run check` включает эту проверку и
сканирование отдельного lockfile на уязвимости. Тесты используют синтетические
данные и модель-заглушку; реальные брокерские и LLM-вызовы не выполняются.
