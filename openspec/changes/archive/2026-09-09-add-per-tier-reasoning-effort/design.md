## Context

Мотивация описана в `proposal.md`. Контракт находится в `specs/per-tier-reasoning-effort/spec.md`.

В `tradingagents/default_config.py` уже есть `_ENV_OVERRIDES` и общие настройки трёх провайдеров с `None` по умолчанию. `TradingAgentsGraph` в `tradingagents/graph/trading_graph.py:108-129` вычисляет один набор параметров для обоих клиентов; `_get_provider_kwargs` переводит общие настройки в параметры провайдера. CLI в `cli/main.py:694-739` выбирает общий reasoning, а при запуске копирует `DEFAULT_CONFIG`. Назначения моделей находятся в `tradingagents/graph/setup.py` и не требуют изменений.

Существующие тесты `test_env_overrides.py`, `test_cli_env_skip.py`, `test_temperature_config.py` и `test_llm_max_tokens.py` дают образцы проверки окружения, выбора CLI и параметров клиентов. Адаптеры уже фильтруют неподдерживаемые модели; Google преобразует `minimal` в `low` для Pro. Новое поведение не требует изменения SDK или этих адаптеров.

## Goals / Non-Goals

**Goals:**
- Использовать существующий путь конфигурации без нового реестра моделей или слоя маршрутизации.
- Разрешать настройку для каждого клиента отдельно, сохранив общие callbacks, temperature, retries и token limit.
- Проверять результат на границе создания клиентов, без сетевых вызовов.

**Non-Goals:**
- Новые провайдеры, отдельные endpoint, настройки отдельных агентов и изменение моделей по умолчанию.
- Универсальная нормализация уровней reasoning, новый режим отключения reasoning и расширение списка поддерживаемых моделей.
- Переработка интерактивного меню или механизма объединения Python-конфигурации с defaults.

## Decisions

### Два необязательных ключа вместо параметров для каждой пары провайдер/тип

Добавить два ключа и две переменные из спецификации в существующий `_ENV_OVERRIDES`; defaults равны `None`. Это меньше и понятнее шести новых провайдерных настроек. Непустые строки сохраняются как есть; отсутствие, `None` и `""` означают наследование. Строка `"none"` не является служебным значением наследования и остаётся значением провайдера, если он её поддерживает. Новую общую enum-валидацию не вводить, поскольку допустимые уровни зависят от модели.

### Разрешение внутри существующего построителя параметров

Расширить `_get_provider_kwargs` необязательным аргументом типа (`deep` или `quick`). Вызов без типа сохраняет общее поведение, которое уже используют тесты. Для каждого из двух клиентов вызвать построитель отдельно, выбрать настройку типа перед общей настройкой активного провайдера и передать значение под существующим именем параметра. Не изменять `self.config` при разрешении. Для провайдеров вне текущих трёх ветвей reasoning не передавать.

Callbacks добавить к обоим отдельным словарям, сохранив существующее поведение общих параметров. Альтернатива с временным изменением общей конфигурации отвергнута из-за риска утечки значения deep в quick. Отдельная фабрика или объект конфигурации для двух значений избыточны.

### CLI сохраняет общий выбор как резервное значение

Не добавлять отдельных запросов для deep/quick. Сохранить текущие правила пропуска общего запроса при переменной провайдера или общей переменной reasoning. Новые значения остаются в копии `DEFAULT_CONFIG`, а выбранный общий уровень применяется только как fallback при построении клиентов. При необходимости изменить только сборку конфигурации, если тест выявит потерю новых ключей; не переписывать работающий путь.

Наличие обоих переопределений само по себе не меняет правила общего интерактивного запроса. Это намеренное сохранение существующего поведения, а не отдельный проект оптимизации CLI.

### Проверка и документация по существующим образцам

Расширить тесты env и CLI; добавить компактную параметризованную проверку разрешения и тест перехвата двух вызовов `create_llm_client`, чтобы доказать реальное раздельное подключение. Проверить callbacks и общие параметры, а не только чистую функцию разрешения. Прогнать существующие тесты адаптеров и параметров генерации.

В `.env.example` и README показать две независимые настройки, порядок наследования и ограничения провайдеров. `high`/`low` обозначить примером, не defaults. При обновлении соседних примеров моделей согласовать устаревшие значения `.env.example` с текущим `DEFAULT_CONFIG`, не менять сами defaults.

Для реализации применимы skills `openspec-apply-change` и `ccc`; при изменении кода, связанного с LangGraph, использовать `ecosystem-primer` и `langgraph-fundamentals`. Если потребуется уточнить SDK-параметры, использовать `find-docs`; план не требует новых SDK API.

## Risks / Trade-offs

- Значение подходит не каждой модели: сохранить действующие проверки адаптеров и явно описать ограничение, не обещать универсальную поддержку.
- Общие переменные уже используются: сохранить fallback и тест существующей конфигурации без новых ключей.
- CLI может потерять настройку при копировании: проверить собранную конфигурацию и итоговые параметры клиентов.
- Один словарь параметров может случайно остаться общим: проверить разные значения в двух вызовах фабрики.
- `DEFAULT_CONFIG` вычисляется при импорте: env-тесты должны перезагружать модуль по существующему образцу, не менять эту семантику.

## Migration Plan

Миграция не требуется: старые конфигурации сохраняют поведение. После обновления пользователь при необходимости задаёт одну или обе новые переменные. Для возврата к прежним уровням достаточно удалить новые переопределения. Новые зависимости и изменения сохраняемых данных отсутствуют.
