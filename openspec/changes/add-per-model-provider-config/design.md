## Context

Мотивация описана в `proposal.md`. Изменение затрагивает конфигурацию, граф, CLI и три адаптера, поэтому отдельный design необходим.

Наблюдаемое поведение:
- `default_config.py` уже содержит централизованные ENV-переопределения и отдельный reasoning для deep/quick; новые настройки следуют этому шаблону.
- `trading_graph.py:108-128` создаёт два клиента с общими provider/URL; `_get_provider_kwargs()` выбирает reasoning и имя лимита токенов по общему provider.
- `cli/main.py` выбирает общий provider/URL, проверяет только его ключ и передаёт его обоим меню моделей. `_build_run_config()` копирует defaults, но безусловно перезаписывает три общих reasoning-ключа значениями selections.
- В `OpenAIClient` reasoning отбрасывается regex-проверкой, в Anthropic действует проверка имени/версии, Google переписывает `minimal` для `pro`. Эти ограничения прямо закреплены текущими тестами и основной спецификацией; delta намеренно заменяет контракт.
- `GoogleClient` уже принимает `base_url`. Azure/Bedrock имеют собственные механизмы endpoint и не используют этот аргумент: расширять их endpoint API не требуется. Azure уже пропускает `reasoning_effort` в конструктор, поэтому достаточно изменения графа.

## Goals / Non-Goals

**Goals:**
- Минимальные изменения существующего flat-конфига (плоского словаря), без новой конфигурационной подсистемы.
- Независимое разрешение подключения и provider-specific kwargs в двух существующих точках создания клиентов.
- Проверяемая передача исходящих значений; серверная поддержка конкретной модели не подменяется локальными догадками.

**Non-Goals:**
- Реестр пользовательских подключений, aliases, импорт JSONC, новые меню, новые зависимости или новые параметры авторизации.
- Новая поддержка reasoning-протокола Bedrock или endpoint-механизмов Azure/Bedrock.
- Изменение нормализации `.content`, DeepSeek `reasoning_content`, MiniMax `reasoning_split`, structured-output capability checks, streaming, агентов и checkpointing.
- Исправление несовместимых сочетаний общего URL и индивидуального провайдера за пользователя.

## Decisions

### 1. Четыре необязательных ключа вместо реестра

Добавить `deep_think_llm_provider`, `quick_think_llm_provider`, `deep_think_llm_backend_url`, `quick_think_llm_backend_url` с `None` и ENV-именами из новой спецификации. Существующие имена моделей не менять; в примере Google сразу задавать `gemini-3.8-flash-high`, без alias `gemini-3.8-flash`.

Альтернатива: вложенный реестр по образцу OpenCode. Отклонена как лишняя для двух существующих моделей. OpenCode не является runtime-зависимостью.

### 2. Независимое наследование без условной защиты URL

Для каждого `tier`:

```text
provider = config[tier + "_think_llm_provider"] or config["llm_provider"]
URL      = config[tier + "_think_llm_backend_url"] or config.get("backend_url")
```

Отсутствующие индивидуальные ключи читать безопасно; provider нормализовать по существующему правилу нижнего регистра. Пустой общий URL трактовать как отсутствие. Не мутировать конфиг.

Это правило явно подтверждено пользователем: **даже при другом индивидуальном provider общий URL наследуется**. Альтернатива с переходом на provider default при несовпадении отклонена. Если URL не разрешён, оставить существующий fallback адаптера, в том числе provider ENV и ошибку обязательного URL у `openai_compatible`.

Отдельный routing layer не нужен. Компактное разрешение в существующем графе и CLI предпочтительнее новой абстракции; совпадение поведения закрепить end-to-end тестом конфигурации.

### 3. Kwargs выбираются по разрешённому provider

`_get_provider_kwargs(tier)` должен использовать фактический provider соответствующего типа, а вызов без tier сохранять общий provider. Существующую проверку `is_openai_compatible()` переиспользовать вместо копирования registry.

| Provider | Общий fallback reasoning | Параметр |
| --- | --- | --- |
| Google | `google_thinking_level` | `thinking_level` |
| Anthropic | `anthropic_effort` | `effort` |
| OpenAI-совместимое семейство, Azure | `openai_reasoning_effort` | `reasoning_effort` |
| Bedrock | не добавляется | не добавляется |

Индивидуальный reasoning сохраняет приоритет. `None`, отсутствие и пустая строка наследуют; строка `none` и другие непустые значения не преобразуются. `max_output_tokens` выбирается только для фактического Google. Temperature, retries, callbacks и назначения агентов не меняются.

Альтернатива: универсальный reasoning-параметр для всех клиентов. Отклонена: протоколы различаются; удаляем необоснованные фильтры, а не различия API.

### 4. Удалить только исходящие ограничения в адаптерах

OpenAI: удалить `_OPENAI_REASONING_MODEL`, `_supports_reasoning_effort()` и ветку пропуска kwarg; удалить ставший неиспользуемым импорт, если других применений нет. Anthropic: удалить проверку поддержки `effort` по имени модели и неиспользуемые определения. Google: удалить преобразование `minimal` в `low`.

Проверка непустоты перед отправкой остаётся, как и предупреждения каталога о неизвестной модели. Не добавлять catch/retry без reasoning, новый enum или преобразование произвольных строк. SDK может сам отклонить значение: гарантируется передача на границе приложения, а не обход валидации зависимости.

Альтернатива: расширять regex для новых имён. Отклонена: новые модели и gateway aliases снова потребуют правок.

### 5. Минимальная интеграция CLI

Сохранить общий шаг выбора provider/URL и его прежние правила ENV/menu/default. Его результат остаётся общим fallback, включая URL, полученный из меню или provider default. Это намеренно означает, что индивидуальный Google без URL может унаследовать выбранный общий OpenAI URL; пользователь задаёт отдельный URL при необходимости.

После общего выбора разрешить два фактических provider. Перенести `ensure_api_key()` из двух веток общего выбора в одну проверку уникальных фактических провайдеров; переиспользовать текущую обработку optional keys. Не требовать ключ неиспользуемого общего provider. Если URL-подсказка общего `openai_compatible` не нужна ни одному фактическому подключению, не запрашивать её; если адрес необходим фактическому `openai_compatible` и не задан, сохранить явную ошибку клиента, не вводя новое меню.

Существующие меню моделей вызывать с соответствующим provider. Прежнее правило «одна ENV-модель пропускает оба меню» не менять. Индивидуальные ключи проходят через копию `DEFAULT_CONFIG`, не перезаписываются selections. Общие reasoning-настройки инициализировать существующими config-значениями и заменять только реально выбранное значение; исключить затирание Google-настройки при общем выборе OpenAI. Общий reasoning prompt остаётся прежним и не применяется к несоответствующему провайдеру. Новые menus/skip-оптимизации не нужны.

### 6. Проверки и документация

Переиспользовать `tests/test_env_overrides.py`, `tests/test_per_tier_reasoning_effort.py`, `tests/test_cli_env_skip.py`, `tests/test_cli_config_precedence.py` и три текущих adapter reasoning suite. Для новых сценариев графа выделить `tests/test_per_model_provider_config.py`, не копируя большой декартов набор существующих тестов. Проверить обе перестановки OpenAI/Google, разные URL одного provider, индивидуальный provider без URL, URL без provider, missing/None/empty, отсутствие reasoning, литерал `none`, неизвестные имена моделей, Azure и `openai_compatible`.

На адаптерах проверять аргументы SDK; для Google добавить узкий тест через перехваченный HTTP transport, подтверждающий, что пример `http://localhost:8317/v1beta` формирует путь с одной версией API. Не выполнять запрос к реальному localhost-сервису. Если SDK требует отличающегося представления base URL, минимально адаптировать только Google boundary, сохранив заданный endpoint и прежние URL-сценарии. Не проектировать общий URL rewriter.

В `.env.example` оставить новые ключи закомментированными, в README показать смешанную пару и независимый fallback. Указать существующие ENV-ключи авторизации провайдеров; значения `none` в локальном OpenCode не доказывают keyless-поддержку Python-клиента. Не менять `.env` и не добавлять реальные ключи.

Рекомендуемые skills при реализации: `openspec-apply-change`; для работы с графом `ecosystem-primer` и `langgraph-fundamentals`; для проверки SDK-параметров и URL `find-docs`. Все regression-тесты изолировать от сети, пользовательских ENV и реальных credentials.

## Risks / Trade-offs

- Несовместимые общий URL и индивидуальный provider -> документировать буквальное наследование и явные URL для смешанных протоколов; не исправлять конфигурацию молча.
- Прежде игнорируемый reasoning теперь вызывает ошибку -> явно описать изменение совместимости, тестировать отсутствие скрытого удаления и не обещать серверную поддержку произвольного значения.
- Google SDK иначе собирает versioned URL -> узкий transport-тест и при необходимости локальная адаптация Google, без изменения протокола остальных клиентов.
- Два endpoint одного provider могут требовать разные ключи -> индивидуальная авторизация вне scope, сохраняется общий существующий механизм ключей провайдера.
- Mock factory не доказывает фактическую отправку параметра -> сочетать graph/CLI wiring-тесты с adapter boundary-тестами и Google transport-проверкой; реальные модели не вызывать.

## Migration Plan

Схема данных и миграции не требуются. Без новых provider/URL ключей подключение остаётся прежним; изменения фильтрации reasoning применяются и к старым общим настройкам, что является намеренным изменением совместимости. Для провайдера, отклоняющего reasoning, убрать и индивидуальное значение, и его общий fallback, если требуется не отправлять параметр. Это не универсальный режим отключения reasoning на сервере.

Для перехода на смешанную пару задать существующие имена моделей, новые provider/URL и существующие ключи провайдеров. Откат реализации возвращает прежний routing и фильтры; перед откатом убрать новые настройки, поскольку старая версия их не использует. Основную спецификацию синхронизировать отдельным штатным workflow после реализации, архив не переписывать.
