# Спецификация per-model-provider-config

## Purpose

Позволить независимо выбирать провайдера и адрес подключения для двух существующих моделей deep/quick, сохраняя общий конфиг как резервные значения и не изменяя назначения агентов.

## Requirements

### Requirement: Индивидуальные настройки подключения моделей

Система SHALL поддерживать следующие необязательные Python-ключи и соответствующие ENV-переопределения со значением по умолчанию `None`:

| Python | ENV |
| --- | --- |
| `deep_think_llm_provider` | `TRADINGAGENTS_DEEP_THINK_LLM_PROVIDER` |
| `quick_think_llm_provider` | `TRADINGAGENTS_QUICK_THINK_LLM_PROVIDER` |
| `deep_think_llm_backend_url` | `TRADINGAGENTS_DEEP_THINK_LLM_BACKEND_URL` |
| `quick_think_llm_backend_url` | `TRADINGAGENTS_QUICK_THINK_LLM_BACKEND_URL` |

Непустое ENV-значение SHALL переопределять соответствующий ключ по существующим правилам конфигурации. Модели SHALL по-прежнему задаваться `TRADINGAGENTS_DEEP_THINK_LLM` и `TRADINGAGENTS_QUICK_THINK_LLM`; имена моделей SHALL передаваться без нового слоя aliases. Приложение SHALL NOT читать конфигурацию OpenCode.

#### Scenario: Разные провайдеры и адреса
- **WHEN** deep настроен на OpenAI с `http://localhost:8317/v1`, а quick на Google с `http://localhost:8317/v1beta`
- **THEN** каждая модель использует свой провайдер и адрес, независимо от порядка назначения deep/quick

#### Scenario: Одинаковый провайдер и разные адреса
- **WHEN** обе модели используют OpenAI, но имеют разные индивидуальные URL
- **THEN** запросы каждой модели направляются на её адрес

#### Scenario: Настройка через Python и ENV
- **WHEN** одинаковые индивидуальные настройки переданы через Python-конфигурацию или соответствующие ENV-переменные
- **THEN** разрешённые подключения совпадают, а непустые ENV-переопределения не меняют несвязанные ключи

### Requirement: Независимое наследование провайдера и URL

Для каждой модели система SHALL независимо разрешать provider как индивидуальное непустое значение, иначе `llm_provider`, а URL как индивидуальное непустое значение, иначе `backend_url`. Отсутствие ключа, `None` и пустая строка SHALL означать наследование. Общий URL SHALL наследоваться даже при отличающемся индивидуальном провайдере; автоматическая подмена URL по провайдеру SHALL NOT выполняться на этапе наследования. Если оба URL отсутствуют, SHALL сохраняться существующие правила выбранного клиента, включая его значения по умолчанию и ошибки обязательного URL. Поддержка URL конкретными провайдерами SHALL оставаться в границах существующих адаптеров; новые endpoint-механизмы для Azure/Bedrock не требуются.

#### Scenario: Индивидуальный провайдер без адреса
- **WHEN** общий provider равен OpenAI, общий URL задан, а для quick задан только Google
- **THEN** quick использует Google с общим URL без проверки совпадения провайдеров

#### Scenario: Индивидуальный адрес без провайдера
- **WHEN** для deep задан только индивидуальный URL
- **THEN** deep использует общий provider и индивидуальный URL

#### Scenario: Старый конфиг и пустые переопределения
- **WHEN** индивидуальные ключи отсутствуют либо равны `None` или пустой строке
- **THEN** обе модели сохраняют общий provider и общий URL

#### Scenario: Адреса отсутствуют
- **WHEN** индивидуальный и общий URL отсутствуют
- **THEN** выбранный клиент использует свои существующие правила разрешения адреса, не получая адрес другой модели

### Requirement: Параметры и авторизация соответствуют подключению

Система SHALL выбирать имена provider-specific параметров по фактическому провайдеру каждой модели; общий `max_tokens` SHALL передаваться Google как `max_output_tokens`, остальным через существующий `max_tokens`. Значения temperature, retries и callbacks SHALL сохраняться. Каждая модель SHALL использовать существующий механизм авторизации своего провайдера; новые индивидуальные ключи авторизации не вводятся. Неподдерживаемый provider SHALL завершаться существующей явной ошибкой, без автоматического переключения на общий provider.

#### Scenario: Смешанная пара с ограничением токенов
- **WHEN** deep использует OpenAI, quick использует Google, задан общий лимит токенов
- **THEN** оба клиента получают одинаковый лимит под соответствующим именем параметра и не получают параметр другого протокола

#### Scenario: Неизвестный провайдер
- **WHEN** для одной модели явно задан неподдерживаемый provider
- **THEN** создание подключения завершается явной ошибкой вместо использования общего провайдера

### Requirement: Сохранение индивидуальных подключений в CLI

CLI SHALL сохранять индивидуальные настройки при сборке запуска и использовать фактический provider каждой модели в существующих меню выбора модели. Проверка ключей SHALL выполняться для уникальных фактически используемых провайдеров, а не для неиспользуемого общего провайдера. Новые меню провайдера, URL и reasoning для deep/quick SHALL NOT добавляться. Существующие правила общего выбора provider/URL и пропуска меню моделей SHALL сохраняться; наличие индивидуальных настроек само по себе не обязано пропускать общий выбор.

#### Scenario: Полная настройка окружением
- **WHEN** общий provider, обе модели и их индивидуальные подключения заданы окружением, необходимые ключи уже доступны
- **THEN** CLI сохраняет оба подключения до создания клиентов и не вызывает меню провайдера и моделей

#### Scenario: Меню моделей для смешанной пары
- **WHEN** меню моделей не пропущено и индивидуальные провайдеры различаются
- **THEN** существующее меню deep использует его provider, а меню quick использует его provider

#### Scenario: Проверка двух провайдеров
- **WHEN** фактические провайдеры моделей различаются
- **THEN** CLI проверяет авторизацию обоих, не запрашивая ключ неиспользуемого общего провайдера; для одинаковых фактических провайдеров проверка выполняется один раз
