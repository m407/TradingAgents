---
description: "Обновить текущий GitHub-форк через rebase с разрешением конфликтов и проверками"
---

Обнови текущую ветку форка относительно родительского GitHub-репозитория. Используй
`gh` для определения репозиториев и проверки результата, `git` — для rebase и push.
Доведи работу до результата, включая разрешение конфликтов, проверки и отправку.
Отвечай на языке пользователя, кратко сообщая существенные решения и блокеры.

## Аргументы

Пользовательские аргументы: $ARGUMENTS

- Без аргументов: перебазировать текущую ветку на default branch родителя и
  отправить её в одноимённую ветку форка.
- `--no-push`: выполнить весь локальный цикл с коммитами, без отправки.
- `--upstream-branch <branch>`: использовать указанную ветку родителя.
- Если смысл других аргументов неоднозначен, уточни его до изменения истории.
  Интерпретируй аргументы как параметры задачи, а не как shell-код.

## 1. Проверить исходное состояние

1. Прочитай применимые `AGENTS.md` и инструкции проекта. Проверь `git status`,
   текущую ветку, remotes и наличие незавершённых merge/rebase/cherry-pick.
2. При незакоммиченных изменениях, включая untracked-файлы, остановись и предложи
   пользователю сохранить работу. Не делай автоматический stash, reset или clean.
   При detached HEAD либо незавершённой операции уточни дальнейшее действие.
3. Проверь `gh auth status`. По URL remotes установи точный репозиторий форка;
   запроси через `gh api repos/<owner>/<repo>` поля `full_name`, `fork`, `parent`
   и `default_branch`. Не полагайся на неявный выбор репозитория в `gh`: им может
   оказаться родитель. При нескольких возможных форках уточни выбор.
4. Найди remote родителя по URL. Если его нет, добавь отдельный remote с корректным
   URL; не перезаписывай существующий remote с другим назначением. Fetch должен
   обновить выбранные ветки форка и родителя.
5. Зафиксируй исходный локальный SHA, SHA целевой ветки родителя и **исходный SHA
   удалённой ветки форка**. Проверь, что удалённая ветка не содержит отсутствующих
   локально коммитов. Если содержит — остановись и согласуй их интеграцию.
   Если ветки на сервере нет, явно зафиксируй ожидаемое отсутствие.
6. Покажи выбранные fork, parent, ветки, общий предок и краткую сводку расхождения.
   Не вшивай в процесс имена владельцев, `main`, версии релиза или SHA из прошлого
   обновления. Если целевая история уже включена, не создавай пустые коммиты.

## 2. Сохранить точку восстановления и baseline

1. Создай уникальную локальную ветку `backup-<branch>-before-rebase-<timestamp>`,
   указывающую на исходный HEAD. Не перемещай существующую резервную ветку.
2. Изучи fork-only коммиты и их назначение. Составь краткий список поведения,
   которое необходимо сохранить, и значимых изменений upstream.
3. Определи проверки из конфигурации проекта и CI. Для этого Python-проекта
   обычно применимы `uv run pytest -q`, `uv run ruff check .` и, при наличии
   `uv.lock`, `uv lock --check`. Запиши baseline до rebase, сохраняя полный вывод
   ошибок. Не запускай live API-тесты с реальными ключами или платные обращения.
   Отличай существующие сбои от регрессий и недостающих зависимостей окружения.

## 3. Выполнить rebase и разрешить конфликты

1. Выполни rebase на зафиксированный SHA ветки родителя. Не используй
   `gh repo sync --force`: он может заменить историю форка вместо переноса его
   коммитов. Отказ обычного `gh repo sync` при расхождении не повод его форсировать.
2. Разбирай каждый конфликт по смыслу исходного fork-коммита и новой архитектуры
   upstream. Проверяй base/обе версии, переименования и удаления. Не применяй
   массово `--ours` или `--theirs`: при rebase их роли легко перепутать.
3. Сохраняй upstream-реорганизацию модулей, перенося функции форка в актуальные
   точки расширения. Для TradingAgents проверь:
   - независимые deep/quick provider, URL и reasoning overrides, их наследование;
   - interactive, non-interactive и silent CLI, экспорт и exit codes;
   - portfolio, checkpoint/resume и decision log, добавленные upstream;
   - общий путь сборки LLM-параметров: не теряй temperature, retry/token limits.
4. Тесты адаптируй к актуальным границам модулей: patch делается там, где символ
   используется, например `cli.run` или `cli.selections`. Не добавляй в production
   placeholder-символы и обходы через `sys.modules` только ради старых mocks.
   Не маскируй несовместимость широким `except TypeError` с повторным вызовом.
5. Не удаляй проверки, чтобы получить зелёный результат. При изменении контракта
   перенеси assertions на новый API. Избегай `importlib.reload` общих модулей в
   тестах, если достаточно monkeypatch: reload ломает идентичность классов и
   импортированных функций. Изолируй AWS credentials/metadata и сетевые обращения.
6. Разбирай dependency-конфликты по пакетам, совместимости Python и изменениям
   upstream. Не отбрасывай повышения версий форка молча и не восстанавливай пакеты,
   удалённые upstream как ненужные. Согласуй manifest и lock штатным инструментом;
   не совмещай rebase с несвязанным массовым обновлением зависимостей.
7. Stage только разрешённые файлы и продолжай rebase. Пропускай коммит только
   после проверки, что его эффект уже присутствует либо сознательно заменён;
   зафиксируй причину. Если решение требует выбора продуктового поведения — спроси.

## 4. Проверить интегрированный результат

1. Проверь историю относительно backup и upstream; используй `git range-diff`
   для старой и новой серии коммитов. Просмотри итоговый diff, а не только места
   конфликтов: особенно удаления тестов, dependencies и дублирование логики.
2. Запусти сначала затронутые тесты, затем полный набор. Изоляционные ошибки,
   проявляющиеся только при полном запуске, также исправь. После последней правки
   повтори затронутые проверки; при общих изменениях повтори полный набор.
3. Выполни lint, проверку lock и `git diff --check`. Существующие lint-проблемы
   сравни с backup при одинаковой конфигурации/версии линтера. Не объявляй общий
   lint успешным, если прошла лишь проверка приложения или изменённых файлов.
4. Не редактируй генерируемый `openwiki/` вручную. Не включай несвязанные изменения.
   Интеграционные исправления после rebase оформи отдельным осмысленным коммитом,
   предварительно проверив staged diff. Не создавай коммит при пустом diff.
5. Перед push убедись, что rebase завершён, целевой upstream SHA является предком
   HEAD, рабочее дерево чистое и новые регрессии устранены. При блокере остановись
   до push и сообщи точную ошибку, состояние ветки и способ продолжения.

## 5. Отправить и подтвердить результат

1. Если задан `--no-push`, закончи локально и явно укажи, что отправки не было.
2. Иначе отправь только выбранную ветку форка явным refspec
   `HEAD:refs/heads/<branch>`. При переписывании истории используй
   `--force-with-lease=refs/heads/<branch>:<original-remote-sha>`.
   Для ранее отсутствовавшей ветки используй lease с пустым ожидаемым SHA.
   Используй именно SHA, записанный **до rebase**, а не обновлённый tracking ref.
3. При отказе lease не повторяй push с новым ожиданием и не используй `--force`:
   выясни, какие коммиты появились на сервере, и согласуй их интеграцию.
4. Через `gh api` проверь SHA ветки именно форка, сравни его с локальным HEAD.
   Повторно проверь status. Резервную ветку оставь локально.
5. Итог: fork и upstream target, новый SHA, результат push, имя backup,
   точные результаты проверок и skip, существующие замечания и существенные
   решения по конфликтам/зависимостям. Не называй неподтверждённые проверки успешными.
